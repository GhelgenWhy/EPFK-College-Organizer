# Маніфест роботи з Git і правила комітів

## 1. Принципи роботи

Незалежно від способу написання коду, автор відповідає за його поведінку, перевірку та пояснення змін.

- Історія Git має пояснювати, що змінилося і навіщо.
- Один коміт містить одну логічну зміну. Пов’язані код, тести та документація можуть бути в одному коміті.
- Незалежні виправлення, нові функції та масове форматування розділяємо.
- Коміт - завершений крок, який можна переглянути та за потреби скасувати.

## 2. Гілки та напрямок злиття

Основний потік:

```text
гілка учасника → dev → main
```

- `main` - стабільний стан проєкту, готовий до випуску.
- `dev` - спільна гілка інтеграції та перевірки роботи команди.
- Кожен учасник має власну постійну гілку, створену від `dev`.
- Учасник комітить у свою гілку. Зміни в чужій гілці погоджує з її власником.
- Прямі робочі коміти в `dev` і `main` не робимо; зміни надходять через pull request (PR).
- Нові функції та виправлення проходять через `dev`, а потім через PR у `main`.

Наявність персональної гілки не означає, що вся робота учасника має чекати одного великого злиття. Інтегруємо невеликі завершені зміни регулярно. PR включає всі ще не злиті коміти гілки: незавершені сторонні задачі не повинні випадково потрапляти до нього.

Перед початком роботи та відкриттям PR оновлюємо інформацію про remote через `git fetch` і синхронізуємо свою гілку з `dev`. Для постійних опублікованих гілок пропонуємо merge, щоб не переписувати історію. Після злиття також синхронізуємо персональну гілку з актуальним `dev`.

## 3. Формат повідомлення коміту

Використовуємо [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/). Повідомлення комітів пишемо англійською.

```text
<type>: <short description>
```

Базовий формат - `feat: ...`, `fix: ...` тощо; за потреби можна використати стандартний необов’язковий scope.

| Тип | Коли використовувати | Приклад |
| --- | --- | --- |
| `feat` | Нова функціональність | `feat: add task deadline reminders` |
| `fix` | Виправлення помилки | `fix: preserve event date when editing` |
| `docs` | Зміни лише документації | `docs: describe local setup` |
| `refactor` | Переробка коду без нової функції чи виправлення помилки | `refactor: extract task validation` |
| `perf` | Покращення продуктивності | `perf: reduce calendar query count` |
| `test` | Додавання або зміна тестів | `test: cover invalid task deadlines` |
| `build` | Збірка, залежності та їх конфігурація | `build: update Vite dependency` |
| `ci` | Налаштування CI/CD | `ci: run backend tests on pull requests` |
| `style` | Форматування коду без зміни поведінки | `style: format backend source files` |
| `chore` | Службові зміни, які не підходять до інших типів | `chore: ignore local editor files` |
| `revert` | Скасування попередньої зміни | `revert: remove task deadline reminders` |

Тип обираємо за метою зміни. Виправлення помилки разом із регресійним тестом - `fix`, а нова функція з тестами - `feat`. `style` означає форматування коду; зміни вигляду інтерфейсу класифікуємо за метою як `feat` або `fix`.

### Заголовок

- Тип пишемо малими літерами, після двокрапки ставимо пробіл.
- Опис починаємо з дієслова в наказовій формі: `add`, `fix`, `remove`, `update`.
- Не ставимо крапку в кінці та не використовуємо повідомлення на кшталт `fix: fixes`, `chore: update stuff` або `feat: done`..
- Описуємо результат зміни, а не факт роботи чи використання AI.

## 4. Що перевіряти перед комітом

1. Переглянути `git status` і diff; переконатися, що зміни відповідають задачі.
2. Додати потрібні файли або фрагменти та переглянути саме staged diff через `git diff --cached`.
3. Прибрати випадкові зміни, тимчасові діагностичні правки та налагоджувальні виводи.
4. Перевірити відсутність паролів, токенів, приватних ключів, локальних `.env` із секретами та персональних даних. Приклади конфігурації містять лише безпечні заглушки.
5. Виконати перевірки, відповідні зміні, і підготувати змістовне повідомлення.

Не комітимо `node_modules`, локальні логи, кеші та артефакти збірки, якщо для них немає окремої погодженої потреби. Lock-файли комітимо разом із відповідними змінами залежностей.

Для змін frontend запускаємо `npm run build` і `npm run lint` у `frontend`. Для змін backend - `npm run build`, `npm run lint`, `npm test` у `backend`; якщо змінюється поведінка API або інтеграція, також `npm run test:e2e`. Для змін лише документації достатньо перевірити зміст, приклади та посилання.

## 5. Історія, конфлікти та скасування

- Не переписуємо історію `dev`, `main` та опублікованих гілок, на які спираються інші учасники.
- Не використовуємо force push у `dev` і `main`. Винятки для персональної гілки попередньо погоджуємо з усіма, кого це зачіпає; за потреби використовуємо `--force-with-lease`.
- Локальні неопубліковані коміти можна впорядкувати перед push, якщо це не зачіпає чужу роботу.
- Спільні зміни скасовуємо через `git revert`, зберігаючи історію. У повідомленні пояснюємо причину та вказуємо коміт, який скасовано.
- Конфлікти розв’язуємо за змістом; якщо намір чужого коду незрозумілий, звертаємося до автора. Після розв’язання повторюємо відповідні перевірки.
